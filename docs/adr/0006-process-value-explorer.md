# ADR 0006 — Process Value Explorer → GTM process converter

**Status:** Accepted 2026-07-10

## Context

The go-to-market launch tracker seeds its board from a generic L1 "Product Manufacture"
process. Until now that process (`shared/src/seed/gtmProcess.ts`) was generated by an
uncommitted scratch script from a gitignored JSON, so it could not be re-derived and it dropped
the process asset's richer columns.

The governed asset is a single **Report** sheet in the Process Value Explorer workbook
(`reference_tasks/Insurance_Product___Process Value Explorer Export.xlsx`): Level 1–4 names +
descriptions, Point of Contact, SLA (in Days), Type of Work, **Value of Work**
(Enables / Directly Contributes / Neutral), a **4E disposition**
(Embrace / Elevate / Enhance / Exclude), and Complex/Simple ActivityFlow order indices.

## Decision

A **deterministic, unit-tested, pure converter** — `shared/src/gtm/processExplorer.ts`
(`convertProcessExplorer(rows)`) — is the single place the workbook's columns become template
tasks. It is re-runnable offline via `scripts/genGtmProcess.ts`, which reads the workbook,
(re)writes the committed fixture `samples/process-value-explorer.xlsx`, and regenerates
`shared/src/seed/gtmProcess.ts`.

Mapping and rules:

- **L2 → `phaseL2`, L3 → `groupL3`, L4 → `taskL4`/title.**
- **4E `Exclude` rows are dropped** — never become tasks. This is the 4E point: the platform
  automates the Embrace / Elevate / Enhance work and drops the Exclude work. The three
  surviving dispositions ride onto each task (`Task.disposition`, additive) for the board's 4E
  filter chips + card tint. `Value of Work` rides along too (`Task.valueOfWork`, additive).
- **SLA → `slaDays`, group-deduped.** A group's SLA is expressed on every row of the group; it
  is assigned to the FIRST KEPT task of the L3 group (siblings `0`) so the backward schedule
  consumes each group's SLA once, not `SLA × rows`. Blank SLA → documented default `0`
  (`DEFAULT_SLA_DAYS`); the `ongoing` sentinel → `slaDays 0` + `ongoing: true`.
- **`phaseOrder` = the L2 phase index (1..5), NOT the Complex flow index.** The back-scheduler
  (`gtm/schedule.ts`) uses `phaseOrder ≤ 4` = pre-launch (back-scheduled to the deadline) and
  `= 5` = governance (post-launch). Repurposing `phaseOrder` to the sparse Complex ActivityFlow
  index would break that pivot, so the Complex-flow ordering instead drives the task **sequence**
  (`globalOrder`, dense over kept rows in workbook order).
- **Point of Contact → `ownerRole`** = the primary role (`"X (Primary); Y"` → `"X"`; blank →
  `"Unassigned"`).

## Consequences

- The seed shrinks from 75 to **65 tasks** (10 Exclude rows dropped: the whole Product Strategy
  and Stakeholder Training groups, plus three Product Deployment rows — "Deploy to production"
  survives). The pre-launch critical path drops from 100 to **90 business days**.
- Every governance task is now `ongoing` (the workbook's truth), so governance pins to launch
  with no due date rather than forward-chaining fictitious dates. `schedule.test.ts` asserts the
  new invariants (90-day path; ongoing == phaseOrder 5, null due).
- `Task.valueOfWork` / `Task.disposition` are **optional + additive** — ad-hoc and legacy tasks
  omit them; no migration. The board gains 4E disposition filter chips (beside the work-type
  filter) and a per-card disposition tint, both token-driven.
- The converter is gate-tested (`processExplorer.test.ts`: Exclude drop, disposition counts,
  SLA dedup, go-live column split, ongoing, one exact end-to-end row). Regeneration is a
  documented offline step, not a gate step.
