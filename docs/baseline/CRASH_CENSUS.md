## Findings (baseline, 2026-07-16, corpus = 4 hagerty fixtures; 17 reference workbooks PENDING)

Evidence source: the table above (live deterministic run), plus code inspection of
`server/lib/import-brain/workbook.js`, `stage0-router.js:46-63`, `stage2-header-lock.js`.

### F-0. The offline parse harness EXISTS (gap finding inverted)

The pre-build worry was that stage-0 might not be invocable without the server or without
touching AI seams. VERIFIED FALSE: `workbook.js` exports `sniffContainer` +
`readWorkbookToStructural` with dependencies only on `import-brain-shared.cjs` and `exceljs`;
`inferLob` and `scoreHeaderCandidates` are pure functions in the shared bundle. The only
piece that is NOT importable standalone is stage0's signal collector
(`collectWorkbookSignals`, unexported, in a module that requires `./ai-call`); this census
replicates its 15 lines verbatim. RESIDUAL DEBT for the build pack: export
`collectWorkbookSignals` from a seam-free module so no replica is needed.

### F-1. Phantom used-range: ARMORED - confirmed by observation, not just by comment

`workbook.js` claims `ws.rowCount is NEVER trusted` (eachRow includeEmpty:false true-extent
scan). Observed: 5 phantom sheets across 3 files (reported area >= 2x real), ALL clamped,
ZERO believed. On the fixtures present, the used-range question is settled in favor of the
armor. Caveat: the nastiest known offender (SECURA whole-column formatting, 1,048,576
reported rows) is in the PENDING 17, so the extreme case is confirmed only by code path,
not yet by this corpus.

### F-2. Macro files: ARMORED (structure-only) - confirmed

`CO_RV125_Rating_Config_Template.xlsm` sniffed as ZIP/XLSM from magic bytes (vbaProject.bin
byte-scan, filename ignored); worksheets parsed; nothing executed. Wall 2.8s, no crash.

### F-3. Memory amplification: LIVE RISK - the decompression question is NOT settled

The 470KB .xlsm expanded to a 331MB child RSS (~700x). All four files are small, so nothing
failed - but the census could not prove any decompression/zip-bomb armor exists in the live
path (none was found in `workbook.js`: no size cap, no cell-count cap, no decompression-ratio
guard before `wb.xlsx.load(buf)`). A crafted 10MB workbook at this ratio extrapolates to
multi-GB RSS in the App Service host. This is baseline finding number one for the build
pack's armor work.

### F-4. Hidden-sheet policy: behaves as documented

RV125's 4 hidden sheets were excluded from the AI-facing structural model (29 visible) but
fed to the deterministic ISO mapper (peak sheet count 33) - matching the workbook.js policy
comment and the stage0 warning path.

### F-5. Deterministic LOB inference finds NOTHING on real carrier files

All 4 fixtures: `inferLob` -> none (RV125 has 8 refId-shaped tokens, but none match registry
prefixes - correctly not invented). Consequence: on real third-party carrier workbooks the
live stage-0 ALWAYS falls through to the model assist for LOB routing. Not a defect
(flag-not-invent is the invariant), but it means LOB routing on this corpus is 100%
model-dependent - a spend and latency fact the build pack should price in.

### F-6. Deterministic header fast-lock covers 78% of sheets

63/81 scored sheets lock deterministically at >0.80 (best scores ~1.0). The remaining 18
sheets (mostly BRD prose sheets and sparse config sheets) would hit the stage-2 AI fallback.
The deterministic scorer never threw on any sheet, including the 799-merge BRD sheet.

## Hostile self-review

1. **Which workbook came closest to breaking the census scripts, and what defended it?**
   `CO_RV125_Rating_Config_Template.xlsm` - 84,428 cells, 331MB child RSS, 1,145 merges.
   What defended the scripts: per-file child-process isolation with a hard 120s timeout and
   a 64MB stdout buffer, so even a runaway parse would have become a TIMEOUT/CRASH row
   instead of hanging the run. Nothing else came close; all four finished under 4s.

2. **Which v1 expected-trait did the live census contradict?**
   `OH_EnthusiastPlus_BRD.xlsx` was expected to carry `special-char-name` (sheet names like
   `Misc.` and `Fees, Factors, Assesment`), but the live heuristic classifies `.`/`,` as
   ordinary name characters - row marked DRIFT in FIXTURES.md, both values kept. The
   expectation was the error: those names are hostile to humans, not to parsers.

3. **First fixture the build pack's armor work will fail on, and why?**
   Bet: the SECURA whole-column-formatting workbook from the PENDING 17 (or any crafted
   high-compression-ratio file), on MEMORY, not parsing - F-3 shows a 700x RSS amplification
   with zero decompression/cell-count guard before `wb.xlsx.load`. The used-range clamp
   happens AFTER the full workbook is already resident.

4. **What did the crash census PROVE about the used-range and decompression questions the
   two prior docs disagree on - or why could it not prove anything?**
   Used-range: PROVEN (for the present corpus) - 5/5 phantom sheets clamped, 0 believed;
   the eachRow true-extent scan is real behavior, not just a comment. Decompression:
   NOT PROVEN EITHER WAY - the corpus contains no adversarial-compression fixture, so the
   only evidence is the negative code finding (no guard exists) plus the 700x RSS
   observation on a benign file. Settling it needs a crafted fixture in the PENDING pack.

5. **Is any script you wrote capable of mutating a workbook - prove not.**
   `census.mjs` and `crash-census.mjs` touch workbooks exclusively via `fs.readFileSync`
   followed by `ExcelJS.Workbook#xlsx.load(buffer)` / `readFile` (read path). Neither script
   imports or calls any write API (`xlsx.writeFile`, `xlsx.writeBuffer`, cell setters), and
   `grep -n "write" scripts/ops/corpus/*.mjs` shows writes only to `FIXTURES.md`,
   `census.json`, `crash-census.json`, and `CRASH_CENSUS.md` - all outside the fixture
   tree's workbook files. The workbooks' bytes on disk are never opened for writing.
