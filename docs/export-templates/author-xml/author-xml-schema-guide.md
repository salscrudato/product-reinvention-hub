This document describes the format an export/import tool must PRODUCE. It is derived from the real product files, not from the runtime engine schemas. Where the engine `.xsd` and the real XML disagree, the real XML is treated as authoritative and the conflict is noted. ASCII only. Executive summary Author XML is an XML configuration language ("ManuScript") that defines an insurance product: its data model, its rating and business logic, its interview/UI, its forms, and its integrations. One file is one manuscript version (root `<ManuScript>`, SP3:1). The defining property is that a product file is an OVERLAY, not a standalone document. Each manuscript names a parent via `properties@inherited` (SP3:2, `inherited="Carrier_SampleProductBase_3_0_0_0"`). The engine composes the full product by walking the base chain and applying each overlay on top. Inside an overlay a node either OVERRIDES an inherited node of the same `id` (marked `override="1"`) or is NET-NEW (a new `id` not present in any base). This override-vs-new distinction is the core of the format. A second subtlety: the MODEL (data/objects/rules) and the PAGES (presentation) can inherit from DIFFERENT parents. `properties@inherited` gives the base for the item/model chain; `properties@inheritedPage` (BASE:2) gives a separate base for the pages. Captions are resolved through per-culture `.resx` sidecars keyed by a deterministic key built from the node id. A manuscript has three big layers: the model (`<model>` with nested `<object>` and `<public>`/`<private>` fields plus `<table>` rating tables), the presentation (either classic `<topics>/<page>` or newer `<modelCollections>/<viewModel>`), and cross-cutting sections for forms (`<documents>`), integration (`<schemaMaps>`, `<mapping>`) and premium bookkeeping (`<writtenConfig>`). --- ## 2. Inheritance model ### 2.1 The base chain (reconstructed from `properties@inherited`) Each file declares its parent on the single top-level `<properties>` (SP3:2; XSD attr doc at XSD:78: "Used to indicate the manuscript ID the item is derived from, used by inheritance"). Following the `manuscriptID` pointers: ``` DCT_SampleProduct_3_0_0_0 (SP3:2 inherited=Carrier_SampleProductBase_3_0_0_0) | +- Carrier_SampleProductBase_3_0_0_0 | file: ManuScripts/DCTSampleProducts/Base/CarrierAdmin/Carrier_SampleProductBase3.xml:2 | inherited=DCT_ProductBase_1_0_0_0 productCode=Pages | +----- DCT_ProductBase_1_0_0_0 file: ManuScripts/DCTBaseProducts/Base/Admin/DCT_ProductBase.xml:2 inherited="" (root of this chain) productCode=Pages ``` The v1 product SP1 has the same shape one version back (`inherited="Carrier_SampleProductBase_1_0_0_0"`, SP1:2). A separate, parallel chain in the DCTTemplates tree demonstrates the model-vs-pages split explicitly (see 2.2): ``` BaseProduct (BASE:2) inherited = Carrier_ProductBase_Data_3_0_0_0 (the DATA/model base) inheritedPage = Carrier_ProductBase_Pages_3_0_0_0 (the PAGES base) | Carrier_ProductBase_Pages_3_0_0_0 (ManuScripts/DCTTemplates/CarrierAdmin/Admin/Carrier_ProductBase_Pages_3_0_0_0.xml) inherited = Carrier_ProductBase_Data_3_0_0_0 inheritedPage = DuckCreekTech_ProductBase_Pages_3_0_0_0 productCode=Pages | Carrier_ProductBase_Data_3_0_0_0 (ManuScripts/DCTTemplates/CarrierAdmin/Admin/Carrier_ProductBase_Data_3_0_0_0.xml) inherited = DuckCreekTech_ProductBase_Data_3_0_0_0 productCode=Data ``` ### 2.2 MODEL and PAGES inherit from DIFFERENT parents [CONFIRMED @ BASE:2 and XSD:457]. A "Pages" manuscript points its `inherited` attribute at its DATA base (the model it presents) and its `inheritedPage` attribute at a separate PAGES base (the presentation it overlays). Example, `Carrier_ProductBase_Pages_3_0_0_0`: ``` inherited = Carrier_ProductBase_Data_3_0_0_0 (model comes from here) inheritedPage = DuckCreekTech_ProductBase_Pages_3_0_0_0 (pages overlay this) ``` XSD:457 documents `inheritedPage`: "Used to indicate the manuscript ID the Page is derived from, used by inheritance." The `productCode` keyInfo (SP3:24) labels the manuscript's kind: `Data`, `Pages`, `ViewModel`, `Forms`, `Tax`, `Admin`. SP3 carries `productCode="Pages,ViewModel"` (it ships both presentation layers). When `inheritedPage` is ABSENT (as on SP3), the pages inherit from the same parent as `inherited`. The `inherited` attribute can also appear on individual ITEMS (not just `properties`) to record where that specific node came from. Example: in SP3, `<documentSet ... inherited="DCT_ProductBase_1_0_0_0" override="1">` (SP3:11078) and `<comments idref="..." inherited="DCT_ProductBase_1_0_0_0">` (SP3:11720). These record that the item was pulled forward from an ancestor two levels up the chain. ### 2.3 Override vs net-new (the core distinction) Every concrete node in an overlay is one of two things: - OVERRIDE: it carries `override="1"` and/or restates an `id` that exists in a base. It REPLACES the inherited node of that id. The engine merges the overlay's children/attributes over the inherited definition. - NET-NEW: its `id` does not exist in any base and it has no `override` attribute. It is a brand-new node contributed by this overlay. Confirmations from the files: - `<public id="RiskInput.Details" ... override="1">` (SP3:964). The id `RiskInput.Details` exists in the base `DCT_ProductBase.xml` (1 hit) -> this is an OVERRIDE. - `<public id="ManuScriptCoverageInput.Description" path="Description" type="string" override="1">` (SP3:1743). The id exists in `DCT_ProductBase.xml` (1 hit); absent from the immediate parent `Carrier_SampleProductBase3.xml` (0 hits). OVERRIDE that reaches two levels up the chain. - `<private id="Coverage_RiskAPrivate.LimitFactor" ... path="LimitFactor">` (SP3:1452). The id is present ONLY in SP3 (0 hits in either base) and has NO `override` attribute -> NET-NEW. Observed `override="1"` counts in SP3 by node type: `public 51, private 39, object 7, documentSet 2, modelCollection 1, table 1`. Practical rule for an exporter: emit `override="1"` on any node whose `id` you are restating from a base you inherit; omit it (and choose a fresh id) for a new node. Do NOT flatten - the overlay must contain only the deltas plus whatever abstract scaffolding it re-declares. ### 2.4 Abstract scaffolding Nodes may carry `abstract="1"`. An abstract node is a schema/grouping scaffold that is NOT instantiated as data by itself; concrete children live under it. In SP3, 219 of 547 `<object>` elements are `abstract="1"` (for example `<object id="PolicyAdmin" abstract="1">`, SP3:5352, and the `LineCoverages`/`ManuScriptCoverage` scaffolds at SP3:1738-1740). Abstract also appears on `topic`, `page`, `modelCollection`, `minOccurs`, `maxOccurs`, `table`. Overlays commonly re-declare the abstract ancestor path (abstract objects) so that a concrete override can be nested at the right place in the tree; that re-declaration is itself an override of the scaffold. ### 2.5 Version evolution of the presentation layer SP1 (v1) uses the classic pages layer: 8 `<topic>`, 0 `<modelCollection>`. SP3 (v3) uses the ViewModel layer: 9 `<modelCollection>` / 28 `<viewModel>`, with `<topics>` reduced to 2 abstract stubs (SP3:11823, `<topic name="MainInterview" abstract="1">`). The product migrated its presentation layer between versions while keeping the same model. An importer must accept both layers. --- ## 3. Node reference Each element below lists: purpose, parent(s), children, key attributes, a real example (file:line), and a category tag (structural / data / presentation / logic / reference / integration / forms / meta). Counts are the union over the sampled files. A complete machine index of all 240 observed elements is in `author-xml-node-index.json`. A recurring pattern to know first: MANY leaf nodes are "value-or-reference" (the XSD `commonOperatorGroup`). They carry EITHER `value="<literal>"` OR `idref="<field id>"` (a pointer to another field's computed value). This applies to `operand`, `argument`, `case`, `otherwise`, `tableRef`, `fieldRef`, `keyRef`, `default`, `then`, `else`, `caption`, and more. ### 3.1 Structural / containment #### `ManuScript` (structural) - Purpose: document root; one manuscript version per file. XSD:2030 "Document level tag. Root of a ManuScript." - Parent: none. Children (observed): `properties`, `model`, `modelCollections`, `topics`, `documents`, `mapping`, `schemaMaps`, `annotations`, `metaData`, `revisions`. (XSD content model via `xs:all`: model, properties, topics, annotations, revisions, mapping, metaData, shredding, documents, sharedData - note it does NOT list `modelCollections`; see the conflict note in 3.7.) - Attributes: none. - Example: SP3:1 `<ManuScript>`. #### `model` (structural) - Purpose: container for the data model plus all calculation/algorithm logic. XSD:2052 "Container for algorithm calculation and data model." - Parent: `ManuScript`. Children: `object` (1..n), `messages`. - Key attributes: `defaultValue` (root output field, e.g. `defaultValue="data.TotalPremiumWritten"`), `override`. - Example: SP3:956 `<model defaultValue="data.TotalPremiumWritten">`. #### `object` (structural) - Purpose: an aggregate node in the data document; corresponds to an element in the runtime data XML. XSD:2069 "Defines the grouping of data elements in the data document in hierarchical nature. The object tag will correspond to an aggregate element within the data XML document." - Parent: `model`, `object` (nests). Children: `minOccurs`, `maxOccurs`, `public`, `private`, `object`, `table`, `relationships`, `descriptors`, `nameValues`. - Key attributes: `id` (required), `path` (XPath into the data doc; supports predicates, e.g. `path="coverage[Type=&quot;ManuScriptCoverage&quot;]"`, SP3:1739), `abstract`, `override`, `inherited`, `caption`, `document`, `fragment`, `share`, `comment`. - Example: SP3:957 `<object id="data" path="data">`. #### `minOccurs` / `maxOccurs` (structural) - Purpose: record cardinality for the parent object in the data doc. The engine auto-creates records up to `minOccurs` and trims above `maxOccurs`. XSD:2108/2122. `maxOccurs value="*"` means unbounded. - Parent: `object`. Children: none. Attributes: `value` or `idref`, `override`, `inherited`, `abstract`. - Example: SP3:958-959 `<minOccurs value="1" /> <maxOccurs value="1" />`. #### `relationships` / `relationship` / `relatedObject` / `foreignKey` (structural) - Purpose: declares a model-level foreign-key relationship between objects. - Parent chain: `object > relationships > relationship > {relatedObject, foreignKey}`. - Attributes: `relatedObject@idref` (the target object), `foreignKey@idref` (the field holding the FK). - Example: SP3:1731-1735 `<relatedObject idref="Location" /><foreignKey idref="RiskInput.LocationID" />`. #### `schemaGroups` / `schemaGroup` (structural) - Purpose: names groups of schema fields (seen 92 times in SP1/SP3). Child `schemaGroup` carries only `name`. - Example: present in SP3 model region; `schemaGroup name="..."`. ### 3.2 Data model fields #### `public` (data) - Purpose: a field ON the data path. XSD:2517 "The public fields ... relate to data elements in the data XML document ... either the input points required from the data XML document or the output values the ManuScript will develop when processed." Every `public` in the corpus has a `path` (656/656) - path is REQUIRED (XSD:2556). - Parent: `object`. Children: `definition`, `rules`, `worksheet`, `nameValues`, `descriptors`. - Key attributes: `id` (req), `path` (req), `type` (req; int/float/string/ date/bool), `override`, `class`, `comment`, `index`, `alwaysRun`, `abstract`, `inherited`. - Example: SP3:1743 `<public id="ManuScriptCoverageInput.Description" path="Description" type="string" override="1">`. #### `private` (data) - Purpose: an INTERNAL field with a name but (usually) no data-doc representation - a compute/scratch value. XSD:3235 "Private defines internal fields. When a value needs to be named as a field within the ManuScript, but does not have any representation within the data XML document, a private tag will be used." Only 184 of 968 privates carry a `path`; most have none. Public vs private is exactly this: public is on the data path, private is internal. - Parent: `object`. Children: `value`, `affects`, `definition`, `misc`, `worksheet`, `nameValues`, `descriptors`. - Key attributes: `id` (req), `type` (req), `caption`, `path` (optional), `override`, `comment`, `alwaysRun`, `class`, `abstract`, `inherited`. - Example: SP3:4508 `<private id="AccountPage.Caption" caption="" type="string">`. #### `definition` (presentation) - Purpose: presentation/constraint metadata that does NOT affect premium. XSD:2574 "Encapsulates all rules that do not affect premium calculation but are used to define the presentation of the field in the Interview process and documentation rendering." - Parent: `public`, `private`. Children (order per XSD): `applicable`, `caption`, `formatMask`, `maxLength`, `options`, `readOnly`, `required`. - Example: SP3:1744-1747 `<definition><caption value="Endorsement" /><maxLength value="30" /></definition>`. #### `caption` (presentation) - Purpose: the field's display label (interview + documentation). XSD:2723. - Parent: `definition`, `worksheet`, `option` (as attribute elsewhere). Children: none. - Key attributes: `value` (literal caption) OR `idref` (pointer to a field that yields the caption string), `type`, `index`. - Examples: literal SP3:1745 `<caption value="Endorsement" />`; pointer SP3:5697 `<caption idref="ExposureGroupPrivate.DescriptionCaption" />`. #### `formatMask` / `maxLength` / `readOnly` / `required` (presentation) - Purpose: display/edit constraints inside `definition`. `formatMask` value is a .NET-style format string; `maxLength value="30"`; `readOnly` may carry a boolean or a ref; `required` marks mandatory input. - Example: SP3:1746 `<maxLength value="30" />`. #### `options` / `option` (presentation) - Purpose: the coded value list for a field. XSD:2662 - options can be static (`option` children), runtime (`request` child), or reference-derived (`codeRef`/`captionRef` against another object). - Parent: `definition`. `options` children: `option`, `request`, `dataService`, `odbc`. - `option` attributes: `value`, `caption`, `captionRef`, `default`, `validRef`. - Example: SP3:6498 `<option value="200" caption="Avon" />`. #### `worksheet` (presentation) - Purpose: enables rating-worksheet output for a field. XSD:2644 "Enables rating worksheet functionality." Children: `caption`, `comparison`, `formatMask`, `summarize`. - Example: SP3:1454-1456 `<worksheet><caption value="Risk A Limit Factor" /></worksheet>`. ### 3.3 Rules and logic #### `rules` (logic) - Purpose: the compute block that DOES affect premium. XSD:2624 "Encapsulates all rules that affect premium calculation. ... The default tag is only accessed if the public data is blank or zero. The affects tag is processed as the last step of execution." - Parent: `public`, `private`. Children (order-significant per XSD): `dependencies`, `forceRerate`, `default`, `minimum`, `maximum`, `nonRating`, `value`, `misc`, `affects`. - Example: SP3:1748. #### `value` (logic) - Purpose: the primary computed value of a field/rule. When present on a `private`, it is the field's compute expression; inside `rules` it is the rating value. - Parent: `private`, `rules`, `else`, `default`. Children: any one logic producer - `comparison`, `if`, `calculation`, `lookup`, `iterator`, `select`, `request`, `session`, `written`, `functionCall`, `external`, `dateAdd`. - Key attributes: `value` (literal), `idref` (pass-through of another field), `resourceString` (localization flag, see Section 6). - Example: SP3:4509 `<value value="Account" resourceString="1" />`; compute form SP3:2288-2290 (see `iterator`). #### `default` / `minimum` / `maximum` (logic) - Purpose: fallback and clamp rules inside `rules`. `default` supplies a value only when the public data is blank/zero (XSD:2628). `minimum`/`maximum` clamp with an optional `message`. - Example: SP3:1749-1755 `<default><calculation> ... </calculation></default>`. #### `if` / `condition` / `then` / `else` (logic) - Purpose: conditional value. XSD:3518 - `condition` yields a boolean; if true, `then` is the value; else `else` (which may be absent, making the result null). - Parent: `value`, `default`, `rowKeys` (as a key selector). Children: `condition` (holds a `comparison`), `then`, `else`. - Example: SP3:1008-1015 ``` <if> <condition> <comparison compare="eq"> <operand idref="RiskInput.LocationID" type="string" /> <operand idref="LocationSchedulePage.CurrentLocationID" type="string" /> </comparison> </condition> <then idref="RiskPrivate.DeleteRiskObjectRq" /> </if> ``` #### `comparison` / `operand` (logic) - Purpose: a boolean predicate. `comparison@compare` is the operator (`eq`, `ne`, `ge`, `gt`, `le`, `lt`, and logical `and`/`or` when a `comparison` nests a `comparison`). `operand` is value-or-reference (XSD:2979). - Parent: `condition`, `where`, `worksheet`, `comparison` (nesting). `operand` parent: `comparison`. - `operand` attributes: `type` (req), `value` OR `idref`. - Example: SP3:1010-1013 (above). #### `calculation` / `argument` (logic) - Purpose: an arithmetic expression. `calculation` holds ordered `argument` children; each `argument@op` is the operator applied (`eq` seeds the accumulator, then `add`, `sub`, `mul`, `div`, ...). XSD:2963 "Argument is a value-or-reference type used to specify an argument within an equation." - `argument` attributes: `op` (req), `type`, `value` OR `idref`, `round`, `roundType`. - Example: SP3:1750-1753 ``` <calculation> <argument op="eq" type="string" value="Endorsement #" /> <argument op="add" idref="ManuScriptCoveragePrivate.CurrentIteration" type="int" /> </calculation> ``` #### `iterator` (logic) - Purpose: loop/aggregate over the instances of a repeating object. XSD:3794 "The iterator tag is used to loop. ... The number of iterations will be controlled by the number of iterations of the object's pathed element ... The value ... will be determined by the scope and action attributes." - Parent: `value`. Children: `reference` (the per-iteration value), `subtotal`, `where` (filter), `orderBy`, `customQuery`, `dependencies`. - Key attributes: `type` (req), `scope` (req, e.g. `all`), `action` (req: `sum`, `current`, `count`, `max`, ...), `idref` (req, the object looped), `includeDeleted`. - Example (premium roll-up), SP3:2288-2290: ``` <iterator type="float" scope="all" action="sum" includeDeleted="1" idref="ManuScriptCoverage"> <reference idref="ManuScriptCoverageOutput.Premium" type="float" /> </iterator> ``` #### `select` / `case` / `otherwise` (logic) - Purpose: multi-branch switch on a referenced field. XSD:3619 - each `case` matches a value (or comma list/range) via its `select` attribute and yields a value-or-reference; `otherwise` is the fallthrough. - Parent: `value`. Children: `case` (1..n), `otherwise`. - `case` attributes: `select` (req, match key), `type` (req), `value` OR `idref`. - Example: SP3:5360-5371 ``` <select idref="CurrentTransaction.Type"> <case type="int" value="1" select="Cancel" /> <case type="int" value="2" select="Reinstate" /> ... </select> ``` #### `affects` (logic) - Purpose: downstream effects fired as the LAST step of a field's execution (XSD:2628). Contains `reference` children pointing at fields to (re)compute or set. - Parent: `private`, `rules`. Child: `reference`. - Example: SP3:1040-1045 ``` <affects> <reference idref="RiskPrivate.GetCoverageSetCurrentGroupIdRq" effect="preEffect" /> ... </affects> ``` ### 3.4 Rating tables #### `table` (data) - Purpose: tabular data accessed by `lookup`. XSD:3263. `tableType` is `local` (data inline), `query` (SQL), or `dataService` (a data-services call). - Parent: `object`. Children: `fields`, `rowKeys` (1..n), `colKeys` (0..n), `data`, plus `query`/`whereKey`/`dataService` for external types. - Key attributes: `id` (req), `tableType` (req), `separator`, `override`, `comment`. - Example: SP3:5336 `<table id="LimitFactor" tableType="local">` (full worked example in Section 7). #### `fields` / `field` (data) [table-column form] - Purpose: names the result columns of a table. `field@name` + `field@type` (XSD:3358 "Defines the name and data type of a field in a table's record data."). - Example: SP3:5337-5339 `<fields><field type="int" name="Value" /></fields>`. - CAUTION: `field` is OVERLOADED. Here it is a table column. In the presentation ViewModel layer, `<field idref="...">` is a field PLACEMENT (Section 3.6). Same tag, different meaning; disambiguate by parent (`fields` vs `group`/`viewModel`). #### `rowKeys` / `colKeys` / `key` (data) - Purpose: the lookup axes. `rowKeys@name`/`@type`/`@find` (find = `eq` or `range`); each `<key value="...">` is one row/column key (XSD:3369). A `key@default="1"` marks the fallback key. When `find="range"`, a key value may be a range like `10-17` or `18>`. - Parent: `table`. `key` parent: `rowKeys`, `colKeys`. - Example: SP3:5340-5346 (see Section 7). #### `data` / `row` (data) - Purpose: the table body. Each `<row value="...">` is one row; when the table has multiple `fields` or `colKeys`, the row is a `separator`-delimited list read left-to-right against fields x columns. - Example: SP3:5347-5354 and the 2-D table CultureCaptions at SP3:6472-6491. #### `lookup` (logic) [table consumer] - Purpose: read a value out of a table. XSD:3765 "used to get a value from one of the table fields." - Parent: `value`, `caption`, `else`. Children (order per XSD): `tableRef` (req), `fieldRef`, `keyRef` (0..n), `manuscriptName`, `precision`, `onFailure`. - Example: SP3:1449-1453 (Section 7). #### `tableRef` / `fieldRef` / `keyRef` (reference) - Purpose: the three pointers inside a `lookup`. XSD:3019/3031/3043: `tableRef` -> the table `id`; `fieldRef` -> the column `name`; `keyRef` -> a named key value pair (`name` must match a rowKeys/colKeys name; value is value-or-reference). Order of `keyRef` does not matter. - Attributes: all are value-or-reference; `keyRef` adds `name` (req), `type` (req). - Example: SP3:1450-1452 ``` <tableRef value="LimitFactor" /> <fieldRef value="Value" /> <keyRef idref="Coverage_RiskAInput.Limit" type="int" name="Limit" /> ``` ### 3.5 References and named values #### `reference` (reference) - Purpose: a pointer to another field, used both to WIRE logic and to PLACE a field on a page. XSD:3202 "Indicates a reference to another field in the ManuScript. When used in a page, the caption attribute can be used to override the caption used for display." - Parent (observed): `affects`, `section`, `grid`, `tableLayout`, `mapping`, `iterator`, `views`(via view). Child: `nameValues`. - Key attributes: `idref` (req, the target field id), `effect` (`preEffect`/`postEffect`/`onChange`/`setValue` in `affects`), `mapId` (index slot in `mapping`), `name`, `caption`, `index`, `compute`, `computeRef`, `onBlur`, `fldClass`, `capClass`, `hoverHelp`, and `ws*` worksheet hints. - Examples: wiring SP3:1041 `<reference idref="RiskPrivate.GetCoverageSetCurrentGroupIdRq" effect="preEffect" />`; index mapping SP3:11681 `<reference mapId="clientName" name="Client Name" idref="AccountInput.Name" />`. #### `nameValues` / `nameValue` (reference) - Purpose: a named parameter bag attached to a request/action/reference/ option. XSD:4136 "Defines the named value to be associated with the parent item. These items will be added to the resulting XML value ... as either attributes or element." - `nameValue` attributes: `name` (req), `value` OR `idref`, `dataType` (`attribute`/`element`/...), `type`. `nameValue` can nest `nameValue`. - Example: SP3:52-58 (inside an `action`). ### 3.6 Presentation There are TWO presentation layers. A product may ship either or both (keyInfo `productCode`). Classic Pages layer: `topics > topic > page > group > {section, grid, tableLayout} > reference`. Fields are placed via `<reference idref="...">`. #### `topics` / `topic` / `page` (presentation) - Purpose: the interview/documentation outline. XSD:4409/4422/4464. `topic@name` unique per manuscript; `page` is the navigable unit. - `page` key attributes: `name`, `caption`, `pageVersion`, `prevPage` (ordering), `validRef`, `override`, `topicIdRef`/`pageIdRef`/ `manuscriptIdRef` (inheritance-map pointers), `calculate`, `metaPage`. - Example: SP3:11825 `<page name="LocationSchedule" caption="Location Schedule" pageVersion="2" prevPage="Pricing">`. - SP1 uses this layer heavily (8 topics); SP3 keeps only abstract stubs. #### `group` (presentation) - Purpose: controls repetition/orientation over an object. Data-model anatomy (public/private field lifecycle end to end) A field's life, using the real rating field `Coverage_RiskAPrivate.LimitFactor` (SP3:1452) and its inputs/outputs: 1. Declaration. The field is declared under an `object` in `model`. Public if it maps to the data doc (has `path`), private if internal. ``` <object id="Coverage_RiskAPrivate"> (SP3, nested under coverage scaffold) <private id="Coverage_RiskAPrivate.LimitFactor" caption="" type="float" path="LimitFactor"> ``` 2. Presentation metadata (`definition`). Optional. Caption, formatMask, maxLength, options, readOnly, required. For an input field this is where the interview label and edit constraints live (see `ManuScriptCoverageInput.Description`, SP3:1744-1747: `<caption value="Endorsement"/><maxLength value="30"/>`). 3. Compute (`value` for a private, or `rules` for a public). Effects (`affects`). After compute, listed `reference@idref` targets fire with an `effect` (preEffect/postEffect/onChange/setValue). Example (`Coverage_RiskAPrivate.ResetLimitB`, SP3:1459; the affects reference at SP3:1462): `<affects><reference idref="Coverage_RiskBInput.Limit" effect="setValue" /></affects>`. 5. Worksheet (`worksheet`). Optional rating-worksheet label: `<worksheet><caption value="Risk A Limit Factor" /></worksheet>` (SP3:1454). 6. Placement. A presentation node references the field: ViewModel `field@idref` (SP3:34) or classic `reference@idref` (SP3:11827+). 7. Localization. If the caption/value is user-facing and localization is active, a resx key is emitted (Section 6). 8. Overlay. In a child product the field is restated with `override="1"` to change any of the above, or left untouched to inherit it. Public vs private, precisely: `public` REQUIRES `path` and represents an input the data doc provides or an output the manuscript writes back (XSD:2517, 656/656 have path). `private` is a named internal value, usually WITHOUT a path (XSD:3235; only 184/968 have one), used for intermediate computations, show/enable flags (e.g. `AccountPrivate.ShowLastName`), and request plumbing. --- ## 6. Localization (the resx binding rule) Captions are held in .NET ResX sidecars, one file per culture (`*.en-US.resx`, `*.de-DE.resx`, `*.it-IT.resx`), 235 `<data>` entries each for SP3. Each entry is `<data name="KEY"><value>text</value></data>`. The rule for literal vs resx-bound: - A string is RESX-BOUND when it is a user-facing caption/label/option/message AND `properties@multiLanguages="1"` is set (SP3:2 has it). The resx KEY is built deterministically from the owning node's id/name plus a role suffix. At runtime the engine looks up the key in the active culture's resx and uses that translation; the string embedded in the XML is the en-US default/ fallback. - A string is LITERAL (never localized, no resx key) when it is machinery: `id`, `path`, `type`, `class`, `index`, `command`, `verb`, `showRef`, `formatMask`, `comment`, id-valued attributes, etc. Resx key grammar (observed): - `Page.<name>.Caption` <- a `viewModel`/`page` `caption` attribute. - `<fieldId>.Caption` <- a field's `definition > caption`. - `<fieldId>.Value` <- a field's `<value ... resourceString="1">`. - `<fieldId>.Caption.Value` <- a caption-holding field's value. - `<fieldId>.Options.<optionValue>` <- an `option@caption`. - `Messages.<ruleId>.<msgKey>` <- a validation `message`. - `Localization.<key>.Value` <- strings parked in a `Localization` bucket object. Three concrete examples (SP3): 1. viewModel caption. SP3:33 `<viewModel name="Account" caption="Applicant" ...>` -> resx key `Page.Account.Caption` -> en-US value "Applicant" (`DCT_SampleProduct_3_0_0_0.en-US.resx:123`, value at :124). 2. resourceString value. SP3:4508-4510 `<private id="AccountPage.Caption" ...><value value="Account" resourceString="1" /></private>` -> resx key `AccountPage.Caption.Value` -> "Account" (`en-US.resx:120`). The `resourceString="1"` flag is the explicit marker that this `<value>` is localizable. 3. field definition caption. SP3:1743-1745 field `ManuScriptCoverageInput.Description` with `<definition><caption value="Endorsement"/></definition>` -> resx key `ManuScriptCoverageInput.Description.Caption` -> "Endorsement". Important finding about THIS product's sidecars: the SP3 en-US/de-DE/it-IT trio is an UNTRANSLATED SCAFFOLD - all three cultures contain identical English text (0 of 233 keys differ between en-US and de-DE). The mechanism is present but the sample was never translated. That the same key grammar is a real translation mechanism is proven by OTHER manuscripts in the repo that ARE translated with identical key shapes, e.g.: - `DuckCreekTech_IssuePolicy_Pages.de-DE.resx`: `Page.IssuePolicy.Caption` -> "Ausgestellter Vertrag". - `DuckCreekTech_Party_Pages_IT_2_0_0_0.de-DE.resx`: `PartyLicenseInput.LicenseStatusCode.Options.CTF` -> "Gezwungen". - `DuckCreekTech_Party_Pages_US_2_0_0_0.de-DE.resx`: `Localization.AccountCharge.Value` -> "Kontogebuehr". An exporter must therefore (a) emit the en-US string inline in the XML, (b) emit a resx `<data>` entry under the computed key for every localizable caption in every declared culture, seeded with the en-US text where no translation exists. --- ## 7. To ADD a new rating field to the Sample Product without disturbing the base, emit a NET-NEW private (fresh id, no `override`), exactly as SP3 does for `Coverage_RiskAPrivate.LimitFactor` (SP3:1452): declare it under the correct (possibly re-declared abstract) object path, give it `type`/`path`, and a `<value>`; no `override` attribute because the id is new. To CHANGE the caption of the inherited field `ManuScriptCoverageInput.Description` (which lives in `DCT_ProductBase`), emit it with `override="1"` and the new `definition`, exactly as SP3:1743 does. The discriminator is mechanical: id exists in a base -> `override="1"`; id is new -> omit override. That is enough to emit both cases. What is NOT fully proven is partial-vs-full replacement on override (Open Question 2), which affects HOW MUCH of the node you must restate, not WHETHER to mark it as an override. ### 4.
